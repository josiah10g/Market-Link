Part 01

Problem Statement

The Problem

Small local businesses — food vendors, tailors, beauty salons, phone repair shops — overwhelmingly rely on informal channels like WhatsApp and phone calls to receive and manage orders. This creates several recurring problems:

  • Orders get lost in long WhatsApp threads with no structured record
  • No inventory tracking — vendors have no reliable way to know what's in stock in real time
  • No order history — neither vendor nor customer has a searchable record of past transactions
  • No status visibility — customers can't track an order without directly messaging the vendor
  • Lost revenue — missed messages mean missed sales, and disorganized fulfillment damages trust

This is the daily operating reality for most small businesses in cities like Abuja, who cannot justify enterprise point-of-sale software, but still need more structure than a chat app offers.

Target Users

RoleWho they areWhat they need
CustomerAnyone browsing and ordering from local vendorsEasy discovery, reliable ordering, order tracking, history
VendorSmall business owner (food, fashion, beauty, repair)Storefront, inventory control, manageable order queue
AdminPlatform operatorVendor vetting, platform oversight, dispute resolution

Proposed Solution

MarketLink gives every vendor a real digital storefront with live inventory, and gives every customer a structured ordering and tracking experience — replacing the informal WhatsApp order with a real pipeline:

Pending → Accepted → In Progress → Ready → Completed — every transition enforced server-side, not just cosmetic.

What Makes MarketLink Different

  • Inventory-aware ordering — not just a listing/contact-seller page; stock is real and enforced
  • Role-based dashboards — customer, vendor, and admin each get a purpose-built interface
  • A real order lifecycle with server-side validated state transitions
  • Built for any local business category, not just food

Core User Journey

1

Customer registers and browses vendor storefronts or the full product catalog

2

Customer adds items to cart (single-vendor cart) and proceeds to checkout

3

Customer provides delivery address, selects payment method, and places the order

4

Vendor receives the order in their dashboard and moves it through the status pipeline

5

Customer tracks live status and receives notifications on every update

6

Once completed, the customer can leave a review; the vendor's rating recalculates automatically

cd backend

Authentication Details

MarketLink uses custom JWT-based authentication — not Supabase Auth. Supabase is used solely as the hosted PostgreSQL database.

  1. Password is hashed with bcryptjs at registration
  2. On login, the backend verifies the hash and issues a signed JWT containing the user's id and role
  3. The frontend stores the JWT in localStorage and attaches it as a Bearer token to every request
  4. Every protected route runs protect then requireRole() before reaching the controller

Layer Responsibilities

Frontend — renders role-specific experiences and holds client state via Context API (AuthContext, CartContext). Never talks to the database directly; all access goes through the REST API.

Backend — middleware (protect, requireRole(), validate, errorHandler) plus one controller per resource containing all business logic, including the order state machine and atomic checkout transaction.

Database — fully relational schema with foreign keys, CHECK constraints, and unique constraints. All financially significant operations run inside explicit SQL transactions with row-level locking.

Authentication Flow

1

User submits login form on the frontend

2

POST /api/auth/login is sent to the backend

3

Backend looks up the user by email, retrieves password_hash

4

bcrypt.compare() verifies the password against the hash

5

Backend returns a JWT signed with the user's id and role

6

Frontend stores the JWT in localStorage, attaches it as a Bearer token to every future request

7

Every protected route runs protect() then requireRole() before reaching the controller — enforced server-side regardless of what the UI shows

Order State Machine

pending
→
accepted
→
in_progress
→
ready
→
completed
cancelled
— reachable from pending, accepted, or in_progress

Transitions are validated server-side against an explicit allow-list in orderController.js. Any request to move an order to a non-adjacent or invalid state is rejected with 400 Bad Request before it reaches the database.

Checkout Transaction Flow

1

Client sends vendor_id, delivery_address, and a list of { product_id, quantity }

2

Backend opens a database transaction (BEGIN)

3

For each item: SELECT ... FOR UPDATE locks the product row and checks sufficient stock

4

If any item fails, the entire transaction rolls back (ROLLBACK) — no partial order is ever created

5

If all items pass: stock is decremented, the order and its order_items are inserted, a notification is created, and a collision-safe order code is generated

6

Transaction commits (COMMIT) — only then is the response sent to the client

Guarantee: an order is either fully placed with correctly decremented stock, or not placed at all.

Design Decisions Worth Defending

ON DELETE RESTRICT on orders.customer_id / vendor_idPreserves financial/audit history — users and vendors are suspended, never hard-deleted.
order_items snapshots product_name and priceHistorical orders stay accurate even if a vendor later renames or re-prices a product.
vendors.rating defaults to NULL, not 0 or 5A vendor with zero reviews displays as "New," not misleadingly pre-rated.
Unique constraint on (order_id, customer_id) in reviewsEnforced at the database level — duplicate reviews impossible even under concurrent requests.
Indexes on every foreign key and filtered columnKeeps lookups fast at this project's scale without needing a caching layer.
